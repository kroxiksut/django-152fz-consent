# Модуль согласий: проверка типов через Pyright

- [К разделу согласий](./README.md)
- [К общей документации](../../README.ru.md)

## Почему Pyright обязателен

В модуле согласий сосредоточена критичная доменная логика:
- вычисление статусов согласия,
- переходы повторного согласия,
- поведение при отзыве,
- контракты сервисного API.

Ошибки типов в этих местах часто проявляются как скрытые регрессии во время выполнения.  
`pyright` позволяет заранее находить несовпадения структур данных, ошибки с `Optional/None` и поломки контрактов.

## Что проверяется

- Сигнатуры сервисного слоя и типы возвращаемых значений.
- Типы служебных структур (`Optional`, объединения, словари полезной нагрузки).
- Форматы данных на границах публичного API.
- Точки интеграции между модулями согласий и куки.

## Область проверки: только исходники (`src/`), без тестов

Гейт (`pyrightconfig.json`) покрывает только `src/`; каталог `tests/` исключён намеренно. Это ограничение инструмента, а не пробел в покрытии:

- `pyright` берёт типы Django из статического пакета `django-stubs`, но **не** запускает *mypy-плагин* `django-stubs`. Именно этот плагин обучает типчекер динамике ORM Django: обратным связям (`record.events`, `purpose.audience_rules`), автогенерируемым id-полям внешних ключей (`user_id`, `purpose_id`, `document_id`), методам стандартного `UserManager.create_user`/`create_superuser` и кастомным действиям `ModelAdmin`.
- В `src/` эти немногочисленные динамические обращения закрыты точечными подавлениями с комментарием. В тестах же они встречаются повсеместно (фикстуры создают пользователей; проверки читают обратные связи и поля `*_id`), что давало ~160 ложных срабатываний `reportAttributeAccessIssue`/индексных при **нуле** реальных багов в исходниках — шум, который похоронил бы настоящую регрессию.
- Поэтому осмысленная проверка типов в тестах требует mypy-плагина `django-stubs` (то есть `mypy`), что отложено до post-alpha. До тех пор `tests/` вне гейта, чтобы сигнал оставался чистым.

Тесты при необходимости можно проверить вручную (ожидаются фрикции django-stubs):

```bash
pyright tests
```

## Обязательный порядок перед PR

Перед созданием PR:
1. Выполнить тесты.
2. Выполнить линтер.
3. Выполнить `pyright` и устранить найденные ошибки типов.

`pyright` является обязательным контрольным этапом качества в репозитории.

## Типовые команды

Linux/macOS:

```bash
python -m pytest
ruff check src tests
pyright
```

Windows PowerShell:

```powershell
python -m pytest
ruff check src tests
pyright
```
