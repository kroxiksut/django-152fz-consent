# Сравнение с django-cookie-consent

- [К разделу cookie](./README.md)
- [К обзору модуля](./overview.md)

Документ помогает выбрать между
[`django-cookie-consent`](https://github.com/django-commons/django-cookie-consent)
и `django-cookies-152fz`. Это не рейтинг качества: пакеты решают пересекающиеся,
но разные задачи.

Сравнение проверено для `django-cookie-consent 1.0.0` и
`django-cookies-152fz 1.0.2` по состоянию на 22 июня 2026 года. Возможности
upstream-пакета могут измениться в следующих версиях.

## Коротко

`django-cookie-consent` — зрелая универсальная библиотека управления группами
cookie и пользовательским выбором. Она особенно подходит проектам, которым
нужны headless-подход, полный контроль над HTML/JavaScript и явная очистка cookie
по имени, домену и пути.

`django-cookies-152fz` — серверный Django-модуль для управляемого cookie-контура:
политика и её редакции, аудируемая серверная история решений, реестр интеграций,
готовый баннер, страница настроек и исполнение необязательных сценариев по
согласию. Он ориентирован на проекты, где cookie-процесс должен быть частью
администрируемого контура согласий.

## Архитектурное различие

В `django-cookie-consent` текущее решение хранится в browser cookie
`cookie_consent`. В ней зафиксированы принятые или отклонённые группы и версия
принятой группы. Модели базы данных описывают группы и cookie, а `LogItem` может
фиксировать действия принятия и отказа.

В `django-cookies-152fz` источником истины для решения является серверная база
данных. Browser cookie с анонимным токеном идентифицирует анонимного субъекта,
но не заменяет серверную запись решения. После входа анонимную запись можно
связать с пользователем.

## Сравнение возможностей

| Область | `django-cookie-consent` | `django-cookies-152fz` |
| --- | --- | --- |
| Основная цель | Универсальное управление группами cookie и выбором пользователя | Управляемый cookie-контур: политика, версии, аудит, реестр интеграций, баннер и runtime |
| Текущее решение | В browser cookie `cookie_consent` | В серверной БД; анонимный сценарий связан с токеном |
| Модель данных | `CookieGroup`, `Cookie`, `LogItem`; журналирование можно отключить настройкой | Категории, записи и события согласия, состояние баннера, редакции политики и баннера, реестр и снимки реестра |
| Аудит | `LogItem`: действие, группа, версия и время; субъект и request-контекст в модели не хранятся | Серверные записи решений и отдельные события аудита с субъектом и техническим контекстом |
| Версионирование | Версия группы — время добавления последней cookie; новая cookie вызывает повторный запрос | Отдельные редакции политики, снимки категорий и реестра, отдельные редакции баннера; изменение представления не обязано устаревать решение |
| Режим согласия | Глобальные opt-in и opt-out режимы | Default-deny для необязательных категорий; действия «принять все», «только обязательные» и индивидуальный выбор |
| Баннер | Разработчик задаёт собственный `<template>`, стили и вызов JS-модуля | Готовый template tag, варианты компоновки, мобильные варианты, тексты, тема и публичная страница настроек |
| Запуск скриптов | Проверки в шаблонах либо callbacks `onAccept`/`onDecline`; внедрение скриптов выполняет проект | Runtime получает разрешённые элементы реестра и загружает зарегистрированные необязательные скрипты по категориям |
| Удаление cookie | Сильный встроенный механизм: `is_deletable`, `domain`, `path`, `CleanCookiesMiddleware` | Стратегии реестра `best_effort_delete` и `adapter_hook`; сложная очистка выносится в адаптер интеграции |
| Настройка интерфейса | Headless-подход с максимальным контролем проекта | Готовый управляемый интерфейс с настройкой через Django admin и возможностью подключить свои CSS/JS |
| Интеграция с другими согласиями | Самостоятельный универсальный пакет | Самостоятельный пакет с необязательной интеграцией через extra `[consent]` |
| Экосистема | ReadTheDocs, отдельный NPM-пакет, coverage и Playwright e2e | Двуязычная документация, готовые RU/EN тексты и общий репозиторий с `django-consent-152fz` |

## Где django-cookie-consent особенно силён

- Простой и давно устоявшийся контракт групп cookie.
- Поддержка opt-in и opt-out сценариев.
- Полный контроль проекта над разметкой, стилями и клиентским поведением.
- Явные `domain` и `path` для cookie и middleware их удаления.
- Headless-интеграция удобна, когда в проекте уже есть собственная дизайн-система
  и frontend-архитектура.

Для обычного международного Django-сайта, которому нужен гибкий consent manager
без готового операторского контура, `django-cookie-consent` может быть более
рациональным выбором.

## Где django-cookies-152fz особенно силён

- Серверная история решения вместо зависимости только от состояния браузера.
- Раздельные сущности политики, баннера, реестра интеграций и их версий.
- Разделение `dismiss`, решения пользователя и устаревшего согласия.
- Анонимные решения с последующей привязкой к вошедшему пользователю.
- Управление политикой, категориями, реестром и аудитом через Django admin.
- Готовый баннер и страница настроек без обязательной frontend-сборки.
- Default-deny runtime для зарегистрированных необязательных скриптов.
- Необязательная связка с `django-consent-152fz`, когда проекту нужен общий
  жизненный цикл согласий на обработку персональных данных.

## Как выбрать

Выбирайте `django-cookie-consent`, если главным требованием являются гибкий
headless-баннер, opt-out режим, минимальная серверная модель решения и точная
очистка известных cookie по домену и пути.

Выбирайте `django-cookies-152fz`, если важны аудируемая серверная история,
версионирование политики, управляемый реестр интеграций, операторская админка,
готовый интерфейс и связь cookie-решений с другими согласиями проекта.

Оба пакета требуют от оператора корректно определить категории, назначение,
сроки хранения и применимые правовые требования. Установка любого из них сама
по себе не обеспечивает юридическое соответствие.
