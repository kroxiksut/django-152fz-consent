# Политика безопасности

[English version](./SECURITY.md)

В репозитории поставляются два независимо версионируемых пакета:
`django-consent-152fz` (жизненный цикл согласий на обработку персональных данных)
и `django-cookies-152fz` (баннер и исполнение cookie). Оба работают с
персональными данными в контексте 152-ФЗ, включая неизменяемый журнал аудита.
Пожалуйста, относитесь к вопросам безопасности соответственно.

## Поддерживаемые версии

Пакеты версионируются независимо друг от друга; всегда обновляйтесь до последнего
релиза каждого. Исправления безопасности выпускаются только для последней
опубликованной версии каждого пакета и ветки `main`.

| Пакет | Версия | Поддержка |
| --- | --- | --- |
| `django-consent-152fz` | последняя опубликованная версия | ✅ |
| `django-cookies-152fz` | последняя опубликованная версия | ✅ |
| любой | более старые или pre-release сборки | ❌ |

> Обновляйтесь оперативно при выходе релиза с исправлением безопасности.

## Как сообщить об уязвимости

Пожалуйста, не создавайте публичных GitHub issue, pull request или discussion по
вопросам безопасности. Публичное раскрытие до выхода исправления создаёт риск для
субъектов персональных данных.

Сообщайте приватно через GitHub:

1. Откройте репозиторий
   [github.com/kroxiksut/django-consent-152fz](https://github.com/kroxiksut/django-consent-152fz).
2. Откройте вкладку **Security** -> **Report a vulnerability**.

Если приватный канал вам недоступен, свяжитесь с мейнтейнером приватно через
GitHub, не создавая публичный issue.

### Что приложить

- затронутый пакет и версию (`django-consent-152fz` и/или `django-cookies-152fz`);
- затронутый модуль или путь и, по возможности, конкретное место в коде;
- минимальный воспроизводимый пример или proof of concept;
- наблюдаемое воздействие: утечка данных, нарушение целостности журнала аудита,
  повышение привилегий и подобное;
- предлагаемое исправление, если оно есть.

Не включайте в отчёт реальные персональные данные; используйте синтетические.

### Чего ожидать

- подтверждение получения отчёта, как только мейнтейнер сможет его разобрать;
- оценку серьёзности и затронутых версий;
- скоординированное исправление и релиз с последующим публичным раскрытием через
  GitHub Security Advisory после выхода исправления;
- упоминание автора отчёта по запросу.

Это open-source проект, сопровождаемый на условиях best-effort; сроки реакции
контрактно не гарантируются.

## Модель безопасности и границы доверия

Ряд механизмов безопасен только при развёртывании согласно документации.
Неправильная конфигурация здесь является наиболее вероятным источником реальных
проблем, поэтому такие места перечислены явно:

- Авторинг HTML-редакций только для доверенных ролей. Тела редакций юридических
  документов и баннера, написанные в HTML, рендерятся без санитизации.
  Ограничьте авторинг HTML-редакций доверенным персоналом.
- IP клиента и `X-Forwarded-For`. В журнале аудита фиксируется IP клиента.
  Доверяйте `X-Forwarded-For` только за корректно настроенным доверенным прокси;
  иначе IP в неизменяемом аудите можно подделать через заголовок.
- Анонимный токен согласия является bearer-секретом. Он передаётся как cookie с
  флагами `Secure`, `HttpOnly`, `SameSite=Lax` и никогда не принимается из
  query-параметров. Обслуживайте сайт по HTTPS и не логируйте токен.
- Неизменяемый журнал аудита. События согласий и cookie работают только на
  добавление и защищены от удаления, включая bulk-delete и retention-сценарии.
  Не обходите immutable-менеджеры.
- CSV-экспорты в админке защищены от CSV formula injection; поля,
  контролируемые субъектом, нейтрализуются при экспорте.
- Исполнение cookie-скриптов использует положительный allow-list источников
  скриптов, а не blocklist.

Полный набор проверенных аудитом мер и инвариантов см. в документации модулей:
согласия (`docs/consent/ru/`) и cookie (`docs/cookies/ru/`), в частности страницы
`invariants`, `configuration` и `operations-admin`.

## Область действия

В области: уязвимости в исходном коде пакетов под `src/`, затрагивающие
конфиденциальность, целостность или доступность данных согласий и cookie, журнала
аудита, а также поверхности admin и API.

Вне области: проблемы, требующие уже скомпрометированной доверенной роли,
задокументированное доверенное поведение вроде авторинга trusted HTML,
уязвимости в сторонних зависимостях, а также находки, применимые только к
развёртываниям, сконфигурированным вопреки документации.
