# CI/CD: раздельная сборка пакетов

В этом репозитории сборка пакетов в CI/CD разделена по модулям для monorepo-структуры.

## Зачем разделять сборку

В репозитории поддерживаются два независимых дистрибутива:

- `django-consent-152fz`
- `django-cookies-152fz`

Они могут иметь разные версии и разный график релизов.  
Раздельные задания CI явно фиксируют границы модулей и предотвращают случайное «смешивание» пакетов.

## Три файла `pyproject.toml`

В репозитории три файла `pyproject.toml` с разными, не пересекающимися ролями:

| Файл | Что собирает | Публикуется на PyPI? |
|------|--------------|----------------------|
| `packaging/consent/pyproject.toml` | только wheel `django-consent-152fz` | **да** |
| `packaging/cookies/pyproject.toml` | только wheel `django-cookies-152fz` | **да** |
| корневой `pyproject.toml` | оба пакета из `src/` сразу | **нет** |

**Корневой** `pyproject.toml` — для **разработки и тулинга**, а не для релиза:

- editable-установка для разработки — `pip install -e ".[dev,test,api]"` (ставит оба
  пакета из `src/`, чтобы тесты видели и consent, и cookies);
- именно из него ставятся все lint/test-джобы в CI;
- хранит общий конфиг инструментов, не нужный пер-пакетным файлам:
  `[tool.ruff]` (линт + формат) и `[tool.pytest.ini_options]`
  (`DJANGO_SETTINGS_MODULE = "tests.settings"`, маркеры).

Два файла **`packaging/*`** — это **только конфиги сборки релиза**: каждый собирает ровно
одну wheel для PyPI. Релизные артефакты берутся из них, никогда из корневого файла.

## Что делает CI

В `.github/workflows/ci.yml` используются отдельные задания:

- `package-consent`: сборка wheel модуля согласий из `packaging/consent`.
- `package-cookies`: сборка wheel модуля куки из `packaging/cookies`.
- `package-install-smoke`: установка обоих собранных wheel и smoke-проверка.

Дополнительно проверяется состав артефактов:

- wheel согласий содержит `django_consent_152fz/*` и не содержит файлов пакета куки;
- wheel куки содержит `django_cookies_152fz/*` и не содержит файлов пакета согласий.

## Почему это важно

- Снижает риск регрессий при релизе изменений, ограниченных одним модулем.
- Делает контракт установки предсказуемым для пользователей.
- Поддерживает независимое развитие модулей в одном репозитории.

## Локальный эквивалент проверок

```bash
python -m pip install -U build
python -m build --wheel --no-isolation --outdir dist/consent packaging/consent
python -m build --wheel --no-isolation --outdir dist/cookies packaging/cookies
```

После сборки проверяется состав wheel и выполняется smoke-проверка установки.
