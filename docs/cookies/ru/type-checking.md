# Модуль куки: проверка типов через Pyright

- [К разделу куки](./README.md)
- [К общей документации](../../README.ru.md)

## Почему Pyright обязателен

Модуль куки содержит чувствительную к типам логику исполнения:
- решения по загрузке сценариев на основе согласия,
- переходы состояний баннера,
- связку редакций и политик,
- формирование полезной нагрузки контрактов событий.

Ошибки типов в этих местах могут ломать поведение в рантайме без явных синтаксических ошибок.  
`pyright` позволяет выявлять такие проблемы заранее на этапе проверки.

## Что проверяется

- Структуры данных runtime-полезной нагрузки и событий.
- Сигнатуры сервисов выбора категорий и работы с реестром.
- Типы данных во views/forms страницы настроек и действий баннера.
- Границы между cookie-runtime и общими сервисными API.

## Область проверки: только исходники (`src/`), без тестов

Гейт (`pyrightconfig.json`) покрывает только `src/`; каталог `tests/` исключён намеренно. Это ограничение инструмента, а не пробел в покрытии:

- `pyright` берёт типы Django из статического пакета `django-stubs`, но **не** запускает *mypy-плагин* `django-stubs`. Именно этот плагин обучает типчекер динамике ORM Django: обратным связям (`record.events`, `policy.registry_items`), автогенерируемым id-полям внешних ключей (`user_id`, `policy_revision_id`, `registry_item_id`), методам стандартного `UserManager.create_user`/`create_superuser` и кастомным действиям `ModelAdmin`.
- В `src/` эти немногочисленные динамические обращения закрыты точечными подавлениями с комментарием. В тестах же они встречаются повсеместно (фикстуры создают пользователей; проверки читают обратные связи и поля `*_id`), что давало ложные срабатывания при **нуле** реальных багов в исходниках — шум, который похоронил бы настоящую регрессию.
- Поэтому осмысленная проверка типов в тестах требует mypy-плагина `django-stubs` (то есть `mypy`), что отложено до post-alpha. До тех пор `tests/` вне гейта, чтобы сигнал оставался чистым.

Отдельно отслеживается слабость типизации на стороне исходников: `get_cookie_banner_configuration()` возвращает `dict[str, object]`, поэтому вложенные ключи конфига пока не типобезопасны — запланирован контракт через `TypedDict`.

Тесты при необходимости можно проверить вручную (ожидаются фрикции django-stubs):

```bash
pyright tests
```

## Обязательный порядок перед PR

Перед созданием PR:
1. Выполнить тесты.
2. Выполнить линтер.
3. Выполнить `pyright` и устранить найденные ошибки типов.

`pyright` является обязательным контрольным этапом качества в репозитории.

## Типовые команды

Linux/macOS:

```bash
python -m pytest
ruff check src tests
pyright
```

Windows PowerShell:

```powershell
python -m pytest
ruff check src tests
pyright
```
